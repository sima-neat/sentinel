# Додавання типу пристрою

Ця сторінка призначена для учасників, які хочуть навчити Sentinel виявляти новий вид пристроїв.
Вона описує перевірку інтерфейсу ядра, написання й тестування провайдера та документування нового типу
для розробників застосунків.

## 1. Переконайтеся, що ядро описує пристрій

Кожен провайдер — це код Rust усередині Sentinel, який читає інтерфейси ядра: sysfs, `/proc`, uevent
і ioctl лише для читання (V4L2, ALSA, IIO, media controller тощо). Sentinel не запускає інші програми
й не завантажує стек користувацького простору, як-от libcamera чи GStreamer, для виявлення пристроїв.
Перед початком переконайтеся, що ядро надає відомості про пристрій, потрібні застосункам.

Провайдери камер є робочими прикладами: USB-камери у `src/peripherals/v4l2/`, а MIPI-камери у
`src/peripherals/mipi/`.

## 2. Правила для кожного провайдера

1. **Лише читання.** Опитуйте пристрій; ніколи не налаштовуйте його, не запускайте потік, не отримуйте
   право власності й не змінюйте стан ядра. Відкривайте вузли пристроїв із `O_RDONLY | O_NONBLOCK`.
   Запущений застосунок не повинен помічати виявлення.
2. **Стабільна ідентичність.** `id` запису має залишатися тим самим після перепідключення, перезавантаження
   й перенумерації. Формуйте його зі стабільних атрибутів (топологія шини, серійний номер, ім’я сутності ядра),
   а не з `/dev/videoN`, номера карти або порядку переліку. Додавайте префікс типу: `camera:...`, `microphone:...`.
3. **Охоплюйте клас, а не окремий зразок.** Пристрій на столі — перша тестова фікстура, а не специфікація.
   До написання коду перелічіть відмінності інших членів класу (кількість, формати, діапазони проти дискретних
   значень, відсутні необов’язкові поля, складені пристрої, кілька однакових пристроїв, значення, що змінюються
   під час роботи) і обробіть кожну.
4. **Погіршуйте можливості, а не завершуйтеся помилкою.** Якщо необов’язкового поля немає, пропустіть його.
   Якщо необов’язкову частину не можна прочитати, зазначте причину в записі. Завершуйте сканування помилкою лише
   тоді, коли провайдер не може створити правильний список; Sentinel збереже останні коректні записи й покаже помилку.
5. **Лише факти.** Повідомляйте те, що кажуть пристрій і ядро. Підтримку пристрою компонентом Neat визначають
   правила підтримки цього компонента, а не провайдер.
6. **Обмежена робота.** Провайдер працює всередині демона й не може бути примусово завершений, тому він не повинен
   блокуватися, а несправний або ворожий пристрій не повинен змушувати його працювати нескінченно. Обмежуйте кожен
   цикл переліку 1024 записами (`MAX_ENUMERATION_ENTRIES`), а кожен пристрій — 4096 запитами за сканування
   (`EnumerationBudget`, `MAX_DEVICE_ENUMERATIONS` у `src/peripherals/videodev2.rs`).

## 3. Запис

Провайдер повертає список записів:

```json
{"id": "microphone:usb-1-2.3:1.2", "type": "microphone",
 "provider": "daemon.audio.alsa", "details": {"channels": 2, "formats": ["S16_LE"]}}
```

| Поле | Правило |
| --- | --- |
| `id` | Непорожнє, унікальне серед усіх провайдерів і стабільне (див. вище) |
| `type` | Малі літери, цифри, `_` або `-`, починається з літери; не більше 64 символів; не `id`, `type` або `provider` |
| `provider` | Ім’я провайдера, наприклад `daemon.audio.alsa` |
| `details` | Об’єкт JSON. Його поля є схемою типу, описаною в [типах пристроїв](device-types/README.md) |

У каталозі `details` публікується під ключем з назвою типу:
`{"id", "type", "provider", "microphone": {...}}`. Клієнти читають невідомі типи як JSON, тому тип
з’являється в API, CLI, Insight і `details` Neat Core без змін у них.

## 4. Напишіть провайдер

1. Створіть `src/peripherals/<name>/` (або `<name>.rs`) та реалізуйте трейт `Provider` із
   `src/peripherals/model.rs`:

   ```rust
   impl Provider for MicrophoneProvider {
       fn name(&self) -> &str { "daemon.audio.alsa" }
       // Kernel uevent subsystems that should trigger a rescan.
       fn subsystems(&self) -> &[String] { &self.subsystems } // ["sound"]
       fn discover(&mut self) -> Result<Vec<Record>, ProviderError> { ... }
   }
   ```

2. Зареєструйте його одним рядком у `builtin_providers()` у `src/peripherals/mod.rs`.
3. Зробіть корені файлової системи доступними для ін’єкції (наприклад, `with_roots(sys, dev)`) і сховайте
   виклики ioctl за невеликим трейтом, щоб тести працювали без обладнання. Провайдери камер показують цей шаблон.
4. Зіставляйте помилки з кодами `ProviderError`: `io.permission_denied`, `io.open` або
   `peripherals.discovery_failed`.

## 5. Перевірте його

Запустіть провайдер один раз так, як це зробив би Sentinel, і перегляньте, що саме він додає до каталогу:

```bash
simaai-sentinel peripherals --test-provider daemon.audio.alsa
```

Команда перевіряє записи тими самими перевірками провайдера, що й демон, застосовує правила підтримки,
друкує результат і завершується ненульовим кодом за помилки. ID також мають бути унікальними між провайдерами:
додавайте префікс типу й ключ, специфічний для провайдера.

Модульні тести обов’язкові:

- один тест на кожну вісь варіації з правила 3;
- фікстури, перенесені з реальних знімків пристрою, якщо вони є, і синтетичні фікстури, сумісні з форматом,
  в інших випадках; позначайте, які з них які;
- шляхи помилок: відмова в доступі, зникнення пристрою під час сканування, некоректна відповідь.

Перед запитом на злиття виконайте локально кроки CI репозиторію:
`cargo fmt --check`, `cargo check --locked`, `cargo test --locked` і
`scripts/build_vulcan_package.sh`.

## 6. Задокументуйте тип

Додайте `docs/peripherals/device-types/<type>.md` із [шаблону](device-types/TEMPLATE.md) та внесіть його до
[індексу типів пристроїв](device-types/README.md). Розробники застосунків використовують цю сторінку, щоб читати
ваші записи. Зазначте, яку поведінку перевірено на реальному обладнанні, а яку — лише фікстурами.

- [ ] Стабільний `id` зі стабільних атрибутів і префіксом типу
- [ ] Осі варіації перелічено й кожну перевірено
- [ ] Відсутність необов’язкових даних погіршує можливості, а не спричиняє помилку
- [ ] Вихід `--test-provider` переглянуто
- [ ] Сторінку типу пристрою додано та внесено до індексу
- [ ] Кроки CI репозиторію проходять локально
