# ボードのカメラ構成

カタログの`board`ブロックは、ボードがMIPIカメラ向けにどのように設定されているかを説明します。
具体的には、どのボードであるか、U-Bootがどのオーバーレイを適用するか、
起動したデバイスツリーがどのカメラセンサーを記述しているか、
およびインストール済みのオーバーレイがどのセンサーを記述できるかです。
構成済みの各カメラは、そのセンサーにあたる`camera.mipi`カメラを示すため、
クライアントはカメラの`compatible`を調べ、`supported_sensors`からそれを構成するオーバーレイを見つけられます。
デバイスレコードと同様に、事実のみを報告し、構成を変更することはありません。

このブロックはすべてのスキャンでプロバイダーの後に読み取られるため、`camera_id`は常に
同じカタログの`devices`を参照し、ブロックが変わると`revision`も変化します。
存在しないのは最初のスキャンが完了するまでの間だけです。検出が無効化されている場合、
APIはこれまでどおりHTTP 503を返します。

## フィールド

| フィールド | 出現条件 | 意味 |
| --- | --- | --- |
| `model` | デバイスツリーにある場合 | `/sys/firmware/devicetree/base/model`の値。最初のNULまでを取り、前後の空白を除いたものです。例：`SiMa.ai Modalix SoM 16Gig Board` |
| `overlays` | `fw_printenv -n dtbos`が成功した場合 | U-Bootの`dtbos`変数のエントリのうち`.dtbo`で終わるものを、その順序のまま列挙します。カメラのオーバーレイだけでなく、U-Bootが適用するすべてのオーバーレイが含まれます（PCIe、セキュアブート、フラッシュのオーバーレイも同じ変数を使用します）。どのエントリがカメラを構成するかをSentinelは示しません。センサーを構成するオーバーレイは`supported_sensors`に列挙されます |
| `configured_cameras` | 常に | ライブのデバイスツリーにおける、I2C上のMIPI CSI-2センサー。空の場合もあります |
| `supported_sensors` | 常に | `/boot`配下のオーバーレイファイルが構成するセンサー。空の場合もあります |

各`configured_cameras`エントリ：

| フィールド | 意味 |
| --- | --- |
| `compatible` | ノードの最初の`compatible`文字列。例：`sony,imx477` |
| `dt_node` | デバイスツリーのルートからのノードのパス。例：`/i2cmux@0/i2c@0/imx477@1a` |
| `i2c_device` | I2Cデバイス。sysfsでの名前と同じ`<bus>-<address>`の形式です。例：`5-001a` |
| `data_lanes` | センサーのエンドポイントの`data-lanes`に含まれるセルの数 |
| `camera_id` | このセンサーにあたる`camera.mipi`カメラの`id`。カタログにそのようなカメラがない場合は存在しません |

各`supported_sensors`エントリには、`compatible`と`overlays`（それを構成するオーバーレイの
ファイル名をソートしたもの）があります。エントリは
`compatible`でソートされます。このリストは`/boot`配下のすべてのスロットディレクトリを統合するため、
起動していないスロットにのみインストールされているオーバーレイが含まれることがあります。

## 各情報の取得元

- **ライブのデバイスツリー**は、U-Bootがオーバーレイを適用した後に
  カーネルが起動に使用したものです。これが実際に有効な構成であるため、
  モデルと構成済みのカメラはオーバーレイファイルではなく、ここから取得します。
- **I2Cの`of_node`リンク**は、構成済みのカメラを見つけて照合する手段です。
  `/sys/bus/i2c/devices`内のすべてのI2Cクライアント（名前は`<bus>-<address>`。
  `i2c-N`という名前のアダプターはスキップされます）のうち、`of_node`リンクが
  ライブのデバイスツリー内に解決されるものが候補になります。そのノードが
  `compatible`を持ち、かつその下にある（別のデバイスのノード内ではない）`endpoint`ノードが
  MIPI CSI-2ソースであることを示す`data-lanes`を持つ場合、構成済みのカメラとみなされます。V4L2は
  I2Cセンサーのサブデバイスを`<driver> <bus>-<address>`と名付け、その後に別の単語が続くこともあります
  （`ccs 5-0010 pixel_array`）。そのため、`camera_name`に
  `<i2c_device>`をスペース区切りの独立した単語として含むカメラが、このセンサーにあたります。これにより、
  ベンダー名やセンサー名を比較することなく、正確なデバイスが照合されます。
- **オーバーレイリスト**は、U-Boot環境に保存されている
  プラットフォーム自身の記録です。`fw_printenv`はボード上でその環境が保存されている場所を把握しているため、
  Sentinelはフラッシュを自分で読み取る代わりに、これに問い合わせます。この値は
  U-Bootが次回の起動時に適用するリストです。起動後に変更されていない限り、
  起動時に適用されたリストと同じです。
- **オーバーレイファイル**は、プラットフォームが同梱するオーバーレイです。`*.dtbo`
  ファイルは、`/boot`直下のディレクトリ（たとえばA/Bスロットである`/boot/boot-0/`と
  `/boot/boot-1/`）にあるものがすべて解析されます。センサーとは、前述と同じく
  `compatible`とCSI-2エンドポイントを持ち、オーバーレイがI2Cバスに追加するノードです。
  つまり、名前が`i2c`で始まるノードの下にあるか、ターゲットがそのようなノードであるフラグメント内にあるものです。
  ターゲットは`target-path`によって、または`target`が参照する`__fixups__`内のラベルによって
  指定されます。複数のスロットで見つかったファイル名は1回だけ列挙されます。

別のCSI-2ソースを下に持つCSI-2ソースはブリッジ（たとえば
I2Cマルチプレクサや、GMSLのデシリアライザーとシリアライザー）であり、どちらのリストからも除外されるため、
センサー自体のみが表示されます。

カメラの解像度とフォーマットは引き続きISPから取得され、カメラの
`modes`に含まれます。オーバーレイはこれらを記述しません。

## 上限

検出処理が読み取るのは、最大で1024個のI2Cデバイス、各デバイスのサブツリーの256ノード、
`/boot`とその各ディレクトリの4096エントリ、および1ファイルあたり最大1 MiBのオーバーレイファイル512個までです。
オーバーレイファイルは一度解析され、再度解析されるのは
サイズ、更新時刻、変更時刻、またはinodeが変わった場合のみです。読み取れなかったファイルは
次のスキャンで再度読み取られます。`fw_printenv`は2秒後に強制終了され、
その出力は最大64 KiB、エラー出力は最大4 KiBまで
読み取られます。

## エラー

エラーには`provider: "board"`が付きます。ブロックの残りの部分は引き続き公開されます。

| コード | 発生条件 |
| --- | --- |
| `io.open` | `model`、`/sys/bus/i2c/devices`、デバイスのノード、`/boot`、その中のいずれかのディレクトリ、またはオーバーレイファイルが存在するものの、読み取れない |
| `io.permission_denied` | 同上で、`EACCES`で失敗した場合。または`fw_printenv`が存在するものの、実行できない |
| `peripherals.discovery_failed` | `fw_printenv`が時間内に終了しなかった、または`dtbos`が設定されていないこと以外の理由で失敗終了した（理由には標準エラー出力に出力された最初の行が示されます）。オーバーレイファイルの形式が不正であるか、1 MiBを超えている。オーバーレイファイルが512個を超えている |

スキップされたオーバーレイファイルと読み取れないI2Cデバイスは、
それぞれ1件のエラーにまとめて報告され、最初の問題のコードと理由、およびそれ以外の件数が示されます。`fw_printenv`がない場合、
または変数が`not defined`であると出力して失敗終了した場合（`dtbos`が設定されていないときの
u-boot-toolsの動作）は、エラーなしで`overlays`が省略されます。
それ以外の理由で失敗終了した場合は、エラーとともに省略されます。
デバイスツリー、I2Cデバイス、または`/boot`がないボードでは、
エラーなしで空のリストが報告されます。

## 制限事項

- CSI-2のルールは構造に基づくものです。独自のCSI-2エンドポイントを持ち、
  下にセンサーを持たないデバイスは、カメラでなくても列挙されます。たとえば
  HDMI-CSI-2ブリッジや、センサーが記述されていない
  GMSLデシリアライザーなどです。
- オーバーレイがI2Cバスにセンサーを追加する場合、そのバスのラベルまたはパスが
  `i2c`で始まらなければ、そのオーバーレイは認識されません。
- `data_lanes`はノード順で最初のエンドポイントから取得されます。幅の異なる
  複数のエンドポイントを持つセンサーでは、そのうち1つだけが報告されます。
- エンドポイントに`data-lanes`がないセンサーはCSI-2
  ソースとして認識されないため、`configured_cameras`と`supported_sensors`に含まれません。
- 独自のCSI-2エンドポイントを持つコンパニオンチップは、構成済みの
  カメラとして列挙されます。たとえば、METOAK-DUALオーバーレイの`Metoak,xc9080`です。
  このチップをセンサーとする`camera.mipi`カメラはないため、`camera_id`を持つことはありません。

## 例

Modalix DevKit上のIMX477の例で、
[`catalog-example.json`](catalog-example.json)と同じものです。モデル、デバイスツリーのパス、
I2Cデバイス、オーバーレイ名はDevKitから書き写したものであり、
Sentinelからキャプチャしたものではありません。このブロックは合成テストフィクスチャで検証されています。
オーバーレイが多くインストールされているボードでは、`supported_sensors`により多くのオーバーレイが列挙されます。

```json
"board": {
  "model": "SiMa.ai Modalix SoM 16Gig Board",
  "overlays": ["modalix-som-waveshare-ARDU-IMX477-1CAM.dtbo"],
  "configured_cameras": [{
    "compatible": "sony,imx477",
    "dt_node": "/i2cmux@0/i2c@0/imx477@1a",
    "i2c_device": "5-001a",
    "data_lanes": 2,
    "camera_id": "camera:imx477 5-001a"
  }],
  "supported_sensors": [
    {"compatible": "sony,imx477",
     "overlays": ["modalix-som-waveshare-ARDU-IMX477-1CAM.dtbo"]}
  ]
}
```
